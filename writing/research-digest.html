Case study · research-digest

A research library that shows its work

Twelve hundred papers a week arrive in the categories I follow. This keeps the ones worth reading, and hands them to whichever AI assistant I am working in. The interesting part is not the retrieval. It is that every ranking decision can be checked by hand.

David Neish

Source is public: github.com/dneish2/research-digest-mcp · MIT · pip install -e . and one command to a working library.

fetcharXiv Atom, standard library only
scorehand-built IDF, no model
embedTF-IDF then SVD to 384
serveMCP over stdio, 6 tools

The ranking is arithmetic

The obvious way to rank papers is to ask a model which ones matter. I did not do that, and the reason is not cost. It is that a model gives you an ordering you cannot argue with. When a paper you expected to see is missing, there is nothing to inspect.

So the score is six rules over words you chose:

a multi-word topic appearing verbatim1.00
a single distinctive word0.60
a single common word0.20
three or more of your topics matched+0.30
exactly two matched+0.15
published today, decaying over 30 days+0.20

The 0.20 is the line that earns its keep. In this literature a word like learning appears in nearly every abstract, so matching it carries almost no information. That discount is a hand-built inverse document frequency, and without it the ranking fills with papers that matched nothing but boilerplate.

Every result carries its own derivation, through the MCP tools and in the interface:

matched agentic (distinctive word), evaluation (distinctive word);
+0.15 for spanning 2 topics; +0.18 for being 3 days old.

term matches 0.48   breadth bonus 0.15   recency 0.18   =  0.810

The interface has a tab where you edit a title, an abstract and your topic list, and watch the arithmetic recompute. It is the part I would show someone first. A ranking you can take apart is a different kind of object from one you have to trust.

The vector store refuses to append

Similarity search uses TF-IDF followed by SVD, which compresses a few thousand sparse word columns into 384 dense ones that capture how terms actually co-vary. It runs offline, needs no model download, and works the same on any machine with Python.

It also has a property that is easy to miss: it is fitted to a corpus. Each run derives its own 384 directions from the documents it saw. Vectors from two runs are not comparable even when both are 384 wide.

I know this because the version I was porting from had been appending. Two small incremental batches had written vectors of 16 and 17 columns next to 1,185 of 384, and the index raised on load, which meant two of its five tools failed for every paper while the status endpoint reported ninety-two percent healthy.

The tempting fix is to force the width to 384 and move on. That converts a loud failure into a silent one: the vectors would stack cleanly and the similarity scores would be meaningless.

The crash was the only reason anyone noticed.

So this store records the encoder and a fingerprint of the fit on every row, and replace_all is the only write path. There is deliberately no append.

CREATE TABLE vectors (
    paper_id  TEXT PRIMARY KEY,
    vector    BLOB    NOT NULL,
    dims      INTEGER NOT NULL,
    encoder   TEXT    NOT NULL,
    basis     TEXT    NOT NULL,
    coded_at  TEXT
);

Find two fits in the store and it refuses to compare them, and says which command rebuilds. Refitting thirteen hundred documents takes about a second. A wrong answer you cannot see costs considerably more.

Absence is not a decline

The trends view compares concept counts this week against last. The version I started from would report every concept at minus one hundred percent whenever the fetch had not run, which is not a measurement of the field. It is a measurement of uptime, presented as a finding.

Now a thin week returns no_data and says so in words: not enough papers in this week to compare, 0 this week, 165 previous. This measures how recently you fetched, not what the field is doing.

Nothing in the core

Fetching, scoring, search, trends, the web interface and the MCP server itself are standard library only. No SDK, no framework, no build step. The MCP protocol is one JSON object per line each way, which fits in about three hundred lines and can be driven from a shell when something looks wrong:

$ echo '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | research-digest mcp

numpy and scikit-learn are an optional extra, needed only for similarity. That is not a stylistic preference. It means the install cannot fail on a machine behind a proxy, and it means the tool degrades to a working keyword library rather than to nothing. CI proves it by running the suite twice, the second time after uninstalling both.

What a fresh clone did

Before writing any of this down I cloned the public repository into an empty directory and followed my own README as though I had never seen it.

core installzero third-party packages
first fetch56 papers from arXiv
first search24 of 56 matched, each with its derivation
embed, extra absentnamed the exact command to install it
MCP handshake6 tools listed

That pass found two things worth fixing. A message that said similarity needs numpy without saying how to get it, and a progress line printed before a flush, so an error on standard error overtook it and appeared above the step it belonged to. Neither is interesting. Both are the kind of thing you only see by being a stranger to your own tool for twenty minutes.

Why it is shaped this way

There is a pattern underneath this that I keep arriving at from different directions: a deterministic substrate with a thin generated layer on top, arranged so the generated layer can fail without taking the facts down with it. The papers are fetched, scored and ranked by code. A model is welcome to summarise them afterwards, and if it is unavailable, the library still works.

The same shape holds in the trading terminal, where panels are built from real chain data and only the narrative is a model call. Getting it right here was cheaper, because the cost of a bad answer is a wasted afternoon rather than a wrong number on a screen someone is making decisions from.
